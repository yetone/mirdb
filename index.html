MirDB

A persistent key-value store with memcached compatibility. Get the speed of in-memory caching with the durability of disk-based storage.

Get Started View on GitHub

Key Features

🔌

Memcached Protocol

Drop-in compatibility with existing memcached clients. Use your favorite client library without code changes.

💾

Persistent Storage

Data survives restarts with SSTable-based durability. Never lose your cached data again.

⚡

LSM Tree Architecture

Write-optimized design for high throughput. Efficient compaction keeps read performance fast.

🧸

Built with Rust

Memory-safe, high-performance implementation using Tokio for async networking.

Getting Started

Installation & Running

Clone the repository and build with Cargo:

# Clone the repository
git clone https://github.com/yetone/mirdb.git
cd mirdb

# Build the project
cargo build --release

# Run MirDB server (default port: 12333)
cargo run --release

MirDB runs on the default port 12333. You can configure this in the TOML configuration file.

Basic Usage

Connect to MirDB using any memcached-compatible client. Here's an example using Python:

# Install pymemcache
# pip install pymemcache

from pymemcache.client import base

# Connect to MirDB on default port 12333
client = base.Client(('localhost', 12333))

# Store a value
client.set('mykey', 'Hello, MirDB!')

# Retrieve the value
result = client.get('mykey')
print(result)  # b'Hello, MirDB!'

# Delete the value
client.delete('mykey')

Configuration

Configure MirDB using a TOML file. Here's an example configuration:

# mirdb.toml - MirDB Configuration

# Network address and port
addr = "0.0.0.0:12333"

# LSM tree configuration
max_level = 7
work_dir = "/tmp/mirdb"

# Memory and storage limits
sst_max_size = "100M"
mem_table_max_size = "4M"
mem_table_max_height = 32

# Compaction settings
imm_mem_table_max_count = 16
l0_compaction_trigger = 4

# Block settings
block_size = "4K"
block_restart_interval = 16

Supported Commands

Storage Commands

  • SET - Store a value
  • ADD - Store if key doesn't exist
  • REPLACE - Store if key exists
  • APPEND - Append to existing value
  • PREPEND - Prepend to existing value

Retrieval Commands

  • GET - Retrieve a value
  • GETS - Retrieve with CAS token

Deletion Commands

  • DELETE - Remove a key-value pair

Admin Commands

  • INFO - Get server information
  • MAJOR_COMPACTION - Trigger compaction

Architecture

Write Path

When data is written to MirDB, it follows a carefully designed path to ensure both performance and durability:

Request → WAL → Memtable → Immutable Memtables → L0 SSTs → L1+ SSTs
  • WAL (Write-Ahead Log): First, writes are logged for durability and crash recovery
  • Memtable: Data is stored in an in-memory skip list for fast access
  • SSTables: When memtable is full, data is flushed to sorted string tables on disk

Read Path

Reads traverse from memory to disk, checking each level until the key is found:

Request → Memtable → Immutable Memtables → L0 (linear) → L1+ (binary search)
  • Memtable First: Check the active memtable for the most recent data
  • Immutable Memtables: Search through memtables awaiting compaction
  • Level 0 SST: Linear search through recently flushed files (may overlap)
  • Level 1+ SST: Binary search through sorted, non-overlapping files
