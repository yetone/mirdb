MirDB

A persistent key-value store with memcached compatibility

Drop-in replacement for memcached with data that persists

Get Started View on GitHub

Key Features

Memcached Protocol

Use your existing memcached clients - no code changes required. Full compatibility with the standard memcached text protocol.

Persistent Storage

Data survives restarts with LSM tree architecture and write-ahead logging. Never lose your cached data again.

High Performance

Async I/O with Tokio, efficient skip list memtables, and intelligent compaction for blazing fast operations.

Quick Start

Get up and running with MirDB in minutes

1. Start the Server

Start MirDB with a configuration file:

Terminal 
# Start MirDB server
mirdb -c config.toml

2. Connect to MirDB

Connect using any memcached client or telnet on port 12333:

Terminal 
# Connect with telnet
telnet localhost 12333

3. Store Data with SET

Use the SET command to store a key-value pair:

Memcached Protocol 
# SET command format: set <key> <flags> <ttl> <bytes>
set mykey 0 0 5
hello
STORED

The SET command stores "hello" (5 bytes) with key "mykey", flags=0, and ttl=0 (no expiration).

4. Retrieve Data with GET

Use the GET command to retrieve stored values:

Memcached Protocol 
# GET command: retrieve stored value
get mykey
VALUE mykey 0 5
hello
END

The response shows the key, flags, size, and the stored value "hello".

Supported Commands

Storage Commands

Command Format Description
SET set <key> <flags> <ttl> <bytes> [noreply] Store a key-value pair
ADD add <key> <flags> <ttl> <bytes> [noreply] Store only if key doesn't exist
REPLACE replace <key> <flags> <ttl> <bytes> [noreply] Store only if key exists
APPEND append <key> <flags> <ttl> <bytes> [noreply] Append data to existing value
PREPEND prepend <key> <flags> <ttl> <bytes> [noreply] Prepend data to existing value

Retrieval Commands

Command Format Description
GET get <key1> [<key2> ...] Retrieve one or more values by key
GETS gets <key1> [<key2> ...] Retrieve with CAS token

Deletion Commands

Command Format Description
DELETE delete <key> [noreply] Remove a key-value pair

MirDB-Specific Commands

Command Format Description
INFO info Display database status and server information
MAJOR_COMPACTION major_compaction Trigger manual compaction of the LSM tree

Response Codes

Response Description
STORED Data stored successfully
NOT_STORED Data not stored (condition not met for add/replace)
EXISTS CAS check failed (item has been modified)
NOT_FOUND Key not found (for delete/replace operations)
DELETED Key deleted successfully
ERROR Unknown command or server error
CLIENT_ERROR <msg> Client input error with message
SERVER_ERROR <msg> Server error with message

Configuration

MirDB uses a TOML configuration file. Here are the default values:

Parameter Default Description
addr 0.0.0.0:12333 Listen address
work_dir /tmp/mirdb Data directory
mem_table_max_size 4MB Memtable size before flush
sst_max_size 100MB Maximum SSTable file size
max_level 7 LSM tree levels

Architecture Overview

MirDB uses a Log-Structured Merge-tree (LSM tree) architecture for efficient write operations and persistent storage.

Data Flow

The following diagram illustrates how data flows through MirDB's LSM tree architecture:

Write Request
    │
    ▼
┌─────────┐
│   WAL   │──── Write-Ahead Log for durability
└────┬────┘
     │
     ▼
┌──────────┐
│ Memtable │──── Active in-memory skip list
└────┬─────┘
     │ (when full)
     ▼
┌────────────────┐
│ Imm Memtables  │──── Immutable memtables queue
└───────┬────────┘
        │ (minor compaction)
        ▼
┌───────────────┐
│ Level 0 SSTs  │──── Recently flushed, may overlap
└───────┬───────┘
        │ (major compaction)
        ▼
┌───────────────┐
│ Level 1+ SSTs │──── Sorted, non-overlapping within level
└───────────────┘

Key Components

Memtable

The memtable is an in-memory write buffer implemented as a skip list data structure. All write operations first go to the memtable, providing fast write performance. When the memtable reaches its configured size limit (default 4MB), it becomes immutable and is queued for flushing to disk.

SSTables (Sorted String Tables)

SSTables are immutable on-disk files that store sorted key-value pairs. Each SSTable contains data blocks, an index block for efficient lookups, and a meta block with bloom filters. SSTables are organized into levels, with Level 0 containing recently flushed data and higher levels containing progressively older, compacted data.

Write-Ahead Log (WAL)

The WAL ensures durability by writing all operations to disk before applying them to the memtable. In case of a crash, the WAL is replayed to recover any data that was in memory but not yet flushed to SSTables.

Compaction Process

MirDB uses a tiered compaction strategy to maintain read performance and reclaim space:

Minor Compaction

Flushes immutable memtables to Level 0 SSTables. Triggered when the active memtable reaches its size limit. This process runs in a background thread to avoid blocking write operations.

Major Compaction

Merges SSTables from Level N to Level N+1, removing deleted keys and duplicate entries. Triggered when a level exceeds its size threshold or when Level 0 has too many files (default: 4 files).

Read Path

When reading a key, MirDB searches in the following order for optimal performance:

  1. Active Memtable - Check the current in-memory write buffer first
  2. Immutable Memtables - Search through any memtables awaiting compaction (newest first)
  3. Level 0 SSTables - Linear search through recently flushed files (may have overlapping key ranges)
  4. Level 1+ SSTables - Binary search using index blocks (non-overlapping within each level)
