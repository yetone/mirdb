MirDB

Persistent Key-Value Store with Memcached Protocol

MirDB is a persistent key-value store written in Rust that implements the Memcached protocol. Unlike traditional memcached, MirDB persists your data to disk using an LSM tree architecture, giving you the familiar memcached interface with the durability you need.

Get Started View on GitHub

Key Features

Memcached Compatible

Drop-in replacement using the standard memcached protocol. Connect using any standard memcached client.

Persistent Storage

Data survives restarts with SSTable-based storage on disk. Your data is safely persisted.

High Performance

LSM tree architecture with async I/O built on Tokio for high-performance networking.

How It Works

MirDB uses an LSM (Log-Structured Merge) tree architecture for efficient writes with durable storage. Data flows through multiple stages to ensure both performance and reliability.

Write Path

Every write operation is first recorded in the Write-Ahead Log (WAL) for durability. This ensures that even if the server crashes, data can be recovered from the log. After the WAL write, data goes into the in-memory Memtable (implemented as a skip list) for fast access.

When the Memtable reaches its size limit, it becomes immutable and a new Memtable is created. Background threads handle minor compaction, flushing immutable Memtables to Level 0 SSTables on disk.

Read Path

Reads check the Memtable first for the fastest response on recent writes. If not found, the search continues through immutable Memtables, then SSTable levels starting from Level 0. Level 0 files may overlap, but higher levels are sorted and non-overlapping for efficient binary search.

Compaction Process

Minor compaction flushes Memtables to Level 0 SSTables. Major compaction merges SSTables between levels, maintaining sorted order and reclaiming space from deleted or overwritten keys. This keeps read performance optimal while supporting high write throughput.

Code Examples

Get started with MirDB using any standard memcached client. Here's how easy it is:

Connect to MirDB 
import memcache

# Connect to MirDB server
mc = memcache.Client(['127.0.0.1:12333'])
Store Data with SET 
# Store a value
mc.set('user:1', 'John Doe')

# Store with expiration (60 seconds)
mc.set('session:abc123', 'user_data', time=60)
Retrieve Data with GET 
# Retrieve a value
user = mc.get('user:1')
print(user)  # Output: John Doe

# Delete a value
mc.delete('user:1')

Getting Started

Installation 
# Clone and build from source
git clone https://github.com/yetone/mirdb
cd mirdb
cargo build --release

# Run with configuration
./target/release/mirdb -c etc/mirdb.toml

For more details, see the full documentation on GitHub.

Configuration

MirDB uses TOML configuration files. Customize memory tables, block sizes, and compaction triggers to optimize for your workload.

Example Configuration (etc/mirdb.toml) 
addr = "0.0.0.0:12333"

max_level = 7
work_dir = "/tmp/mirdb"

sst_max_size = "100M"
mem_table_max_size = "4M"
mem_table_max_height = 32

imm_mem_table_max_count = 16

block_size = "4K"
block_restart_interval = 16

l0_compaction_trigger = 4

thread_sleep_ms = 500

Network

Parameter Description Default
addr Listen address and port 0.0.0.0:12333

Memory Tables

Parameter Description Default
mem_table_max_size Max memtable size before flush 4M
mem_table_max_height Skip list max height 32
imm_mem_table_max_count Max queued immutable memtables 16

SSTables & Blocks

Parameter Description Default
sst_max_size Max SSTable file size 100M
block_size Data block size 4K
block_restart_interval Key prefix restart interval 16

Compaction

Parameter Description Default
l0_compaction_trigger Level 0 files before compaction 4
max_level Maximum LSM tree levels 7
thread_sleep_ms Background thread sleep interval 500
