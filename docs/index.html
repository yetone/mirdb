MirDB

A persistent key-value store with Memcached protocol support

MirDB combines the simplicity of Memcached's text protocol with the durability of disk-based storage. Built with Rust and powered by an LSM tree architecture, it offers a seamless drop-in replacement for applications that need persistence without changing their caching layer.

Get Started View on GitHub

Key Features

Memcached Protocol

Full compatibility with the standard memcached text protocol. Use existing memcached clients without any code changes.

Disk Persistence

Unlike in-memory memcached, MirDB persists data to disk using SSTables (Sorted String Tables) for durability.

LSM Tree Architecture

Leverages a Log-Structured Merge-tree approach with memtables, immutable memtables, and multi-level SSTable compaction.

Async Networking

Built on Tokio for high-performance async I/O operations, handling thousands of concurrent connections efficiently.

Write-Ahead Logging

WAL ensures data durability by logging writes before applying them, enabling crash recovery.

Configurable Parameters

Fine-tune performance with configurable memtable sizes, SSTable limits, compaction triggers, and more.

Quick Start

Get MirDB up and running in minutes with these simple steps.

1. Install MirDB

Install MirDB using Cargo, Rust's package manager:

cargo install mirdb

2. Start the Server

Launch MirDB with a configuration file:

mirdb -c /path/to/config.toml

See the Configuration section for available options.

3. Connect and Use

Connect using any memcached client. Here's an example using telnet:

# Connect to MirDB
telnet localhost 12333

Set a Value

Use the SET command to store a key-value pair:

set mykey 0 0 5
hello
STORED

Format: set <key> <flags> <exptime> <bytes>

Get a Value

Retrieve the stored value with GET:

get mykey
VALUE mykey 0 5
hello
END

For more detailed documentation, including all supported commands and advanced configuration options, visit the full documentation.

Architecture Overview

MirDB uses an LSM tree architecture optimized for write-heavy workloads.

Write Request
    │
    ▼
┌─────────┐
│   WAL   │ (Write-Ahead Log for durability)
└────┬────┘
     │
     ▼
┌──────────┐
│ Memtable │ (Active in-memory skip list)
└────┬─────┘
     │ (when full)
     ▼
┌────────────────┐
│ Imm Memtables  │ (Immutable memtables queue)
└───────┬────────┘
        │ (minor compaction)
        ▼
┌───────────────┐
│ Level 0 SSTs  │ (Recently flushed, may overlap)
└───────┬───────┘
        │ (major compaction)
        ▼
┌───────────────┐
│ Level 1+ SSTs │ (Sorted, non-overlapping within level)
└───────────────┘

Configuration

MirDB provides sensible defaults that work well for most use cases.

Parameter Default Value Description
listen_address 0.0.0.0:12333 Network address to listen on
max_lsm_levels 7 Maximum number of LSM tree levels
work_directory /tmp/mirdb Directory for data files
sstable_max_size 100MB Maximum size of SSTable files
memtable_max_size 4MB Maximum size before memtable flush
block_size 4KB Block size for SSTable files
