MirDB

Persistent Key-Value Store with Memcached Protocol

MirDB combines the simplicity and speed of Memcached with durable persistence. Built in Rust with an LSM tree architecture, it provides high-performance key-value storage that survives restarts while remaining fully compatible with existing Memcached clients.

How LSM Trees Work

MirDB uses a Log-Structured Merge-tree (LSM tree) architecture, which is specifically designed for write-heavy workloads. This approach buffers writes in memory before flushing them to disk in sorted batches, providing excellent write performance while maintaining efficient reads.

The Write-Ahead Log (WAL) ensures durability by persisting every write before it's acknowledged, protecting against data loss during crashes. The multi-level SSTable structure allows for efficient range queries and progressive compaction to reclaim space.

Key Benefits

  • Write-optimized: Sequential writes to WAL and memtable minimize disk I/O
  • Crash-safe: WAL ensures no committed writes are lost during failures
  • Space-efficient: Background compaction merges and deduplicates data
  • Scalable: Leveled compaction prevents write amplification at scale

Built with Rust

MirDB is written entirely in Rust, leveraging its memory safety and performance characteristics:

Rust 
// Example: MirDB's key-value storage interface
pub struct Database {
    memtable: Arc<RwLock<MemTable>>,
    sstables: Vec<SSTable>,
}

impl Database {
    pub fn get(&self, key: &[u8]) -> Option<Vec<u8>> {
        // First check memtable, then SSTables
        self.memtable.read().get(key)
            .or_else(|| self.search_sstables(key))
    }
}

Quick Start

Get MirDB up and running in minutes. Follow these simple steps to start using a persistent key-value store with your existing memcached clients.

1 Build from Source

Terminal 
# Clone the repository
git clone https://github.com/pjzhong/mirdb.git
cd mirdb

# Build the project
cargo build --release

# Run MirDB
./target/release/mirdb -c etc/mirdb.toml

2 Configure (Optional)

mirdb.toml 
# Network configuration
addr = "0.0.0.0:12333"

# Storage settings
work_dir = "/var/lib/mirdb"
max_level = 7

# Memory limits
mem_table_max_size = "4M"
sst_max_size = "100M"

3 Connect with Memcached Client

Python Example 
import memcache

# Connect to MirDB using standard memcached client
client = memcache.Client(['localhost:12333'])

# Now use it just like memcached!
client.set('user:1001', 'John Doe')
print(client.get('user:1001'))  # Output: John Doe

Basic Commands

MirDB supports the standard memcached text protocol. Use telnet or any memcached client to interact with the database.

SET - Store a Value

Memcached Protocol 
# set <key> <flags> <ttl> <bytes>
set session:abc123 0 3600 15
{"user_id":1001}
STORED

GET - Retrieve a Value

Memcached Protocol 
# get <key>
get session:abc123
VALUE session:abc123 0 15
{"user_id":1001}
END

DELETE - Remove a Value

Memcached Protocol 
# delete <key>
delete session:abc123
DELETED

Pro Tip

Use the info command to view database status and major_compaction to manually trigger SSTable compaction when needed.

Protocol Reference

MirDB implements the memcached text protocol, enabling compatibility with existing memcached clients. Below is a reference of all supported commands and response codes.

Supported Commands

Command Description
SET Store a key-value pair
GET Retrieve one or more keys
ADD Store only if key doesn't exist
REPLACE Store only if key exists
DELETE Remove a key
APPEND Append data to existing value
PREPEND Prepend data to existing value
GETS Retrieve with CAS token

MirDB-Specific Commands

These commands are unique to MirDB and provide additional database management capabilities.

INFO MirDB Extension

Display database status and level information. Returns details about memtable size, SSTable levels, and compaction status.

MAJOR_COMPACTION MirDB Extension

Trigger manual compaction of SSTable levels. Use this to reclaim disk space and optimize read performance.

Response Codes

Code Meaning
STORED Data stored successfully
NOT_STORED Data not stored (condition not met)
EXISTS CAS check failed
NOT_FOUND Key not found
DELETED Key deleted successfully
ERROR Unknown command or server error
