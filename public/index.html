MirDB

Persistent Key-Value Store with Memcached Protocol

  • Memcached Compatible - Use existing clients with zero code changes
  • Persistent Storage - Data survives restarts via LSM tree architecture
  • Rust-Powered - Built with Rust for safety and high performance

Key Features

Memcached Protocol

Drop-in replacement for existing memcached deployments. Supports SET, GET, DELETE, and more.

LSM Architecture

Efficient writes with background compaction using Log-Structured Merge-tree.

Async Performance

Built on Tokio for high-throughput asynchronous operations.

Getting Started

Get MirDB running in under 5 minutes with these simple steps.

1

Clone and Build

Clone the repository and build with Cargo:

# Clone the repository
git clone https://github.com/yetone/mirdb.git
cd mirdb

# Build with Cargo
cargo build --release
2

Start the Server

Run MirDB with the default configuration:

# Start MirDB server
./target/release/mirdb-server -c etc/mirdb.toml

MirDB listens on 0.0.0.0:12333 by default.

3

Connect to MirDB

Connect using telnet or any memcached client:

# Connect using telnet
telnet localhost 12333
4

Basic Operations

Try these basic SET and GET commands:

# SET a key-value pair
# Format: set <key> <flags> <ttl> <bytes>
set mykey 0 0 5
hello
STORED

# GET the value back
get mykey
VALUE mykey 0 5
hello
END

# DELETE the key
delete mykey
DELETED

Supported Commands

Storage

  • SET - Store a key-value pair
  • ADD - Store if key doesn't exist
  • REPLACE - Store if key exists
  • APPEND - Append to existing value
  • PREPEND - Prepend to existing value

Retrieval

  • GET - Retrieve a value
  • GETS - Retrieve with CAS token

Deletion

  • DELETE - Remove a key

MirDB Extensions

  • INFO - Get server information
  • MAJOR_COMPACTION - Trigger compaction

Architecture

MirDB uses a Log-Structured Merge-tree (LSM) architecture for efficient writes and persistent storage.

Client Memcached Protocol
↓
WAL Write-Ahead Log
Memtable Skip List (In-Memory)
↓ Minor Compaction
SSTable L0 Sorted String Tables
↓ Major Compaction
SSTable L1-L7 Compacted Levels

How It Works

  1. Write Path: Writes go to the WAL (Write-Ahead Log) for durability, then to the in-memory Memtable (skip list)
  2. Minor Compaction: When Memtable is full, it's flushed to disk as an immutable SSTable
  3. Major Compaction: SSTables are periodically merged across levels for optimized reads
  4. Read Path: Reads check Memtable first, then search through SSTable levels
