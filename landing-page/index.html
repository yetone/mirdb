MirDB

A Persistent Key-Value Store with Memcached Protocol

A high-performance, drop-in memcached replacement with persistence guarantees. Use your existing memcached clients without modification while gaining durable storage powered by LSM-tree architecture.

Get Started View on GitHub

Key Features

Memcached Compatible

Existing memcached clients work without modification. Drop-in replacement with full protocol support for get, set, delete, and more commands.

Persistent Storage

Data survives restarts with LSM-tree architecture and SSTable-based storage. Write-ahead logging ensures durability without sacrificing performance.

High Performance

Optimized for speed with skip-list memtable implementation and intelligent compaction strategies for consistent read and write performance.

Configurable

Flexible configuration options for various deployment scenarios. Tune memtable size, compaction triggers, and storage parameters to match your workload.

Usage

MirDB implements the memcached protocol, so you can use any existing memcached client. Here are the most common operations:

Store a Value

$ set mykey 0 3600 5
hello
STORED

Set a key with flags (0), TTL in seconds (3600), and byte length (5)

Retrieve a Value

$ get mykey
VALUE mykey 0 5
hello
END

Retrieve a value by key

Delete a Value

$ delete mykey
DELETED

Remove a key from the store

Architecture

MirDB uses a Log-Structured Merge (LSM) tree storage engine for efficient writes and durable persistence.

Write-Ahead Log (WAL)

The WAL ensures durability by persisting every write to disk before acknowledging it. In case of a crash, MirDB recovers data by replaying the WAL. Each WAL segment corresponds to one memtable and uses Snappy compression for efficient storage.

Memtable

An in-memory skip list data structure that provides O(log n) insert and lookup operations. When the memtable reaches its size threshold (default 4MB), it becomes immutable and is queued for flushing to disk as an SSTable.

SSTables (Sorted String Tables)

Immutable, sorted files stored on disk. Level 0 contains recently flushed data with potentially overlapping key ranges. Higher levels (1-7) maintain sorted, non-overlapping key ranges within each level for efficient binary search lookups.

Compaction

Minor compaction flushes immutable memtables to Level 0 SSTables. Major compaction merges SSTables between levels when Level 0 has 4+ files or when a level exceeds its size threshold (10MB × 10^level). This process removes deleted keys and maintains read performance.
