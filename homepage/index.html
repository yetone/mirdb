MirDB

A Persistent Key-Value Store with Memcached Protocol

Drop-in memcached replacement with durable storage. Built in Rust for performance and reliability.

Get Started View on GitHub

Getting Started

Get MirDB up and running in minutes

1 Clone and Build 

# Clone the repository
$ git clone https://github.com/yetone/mirdb.git
$ cd mirdb

# Build with Cargo
$ cargo build --release

2 Configure

Create a TOML configuration file (e.g., mirdb.toml):

# MirDB Configuration File (mirdb.toml)
addr = "0.0.0.0:12333"

max_level = 7
work_dir = "/tmp/mirdb"

sst_max_size = "100M"
mem_table_max_size = "4M"
mem_table_max_height = 32

imm_mem_table_max_count = 16

block_size = "4K"
block_restart_interval = 16

l0_compaction_trigger = 4

thread_sleep_ms = 500

3 Start the Server 

# Start MirDB server with your config file
$ mirdb-server -c mirdb.toml

# Or use the full path
$ ./target/release/mirdb-server -c mirdb.toml

4 Connect and Use

Connect with any memcached client:

# Connect using telnet
$ telnet localhost 12333

# Or use any memcached client library

Features

Memcached Compatible

Use existing memcached clients and libraries without code changes.

Persistent Storage

Data survives restarts with LSM-tree architecture.

High Performance

Async I/O with Tokio for high concurrency.

Efficient Compaction

Automatic minor and major compaction strategies.

Memory Safe

Rust implementation eliminates memory safety vulnerabilities.

Configurable

TOML-based configuration for all storage parameters.

Quick Start

Connect with any memcached client and start storing data

# Connect to MirDB
$ telnet localhost 12333

# Store a value (persists across restarts)
SET mykey 0 0 5
hello
STORED
# Retrieve stored data
GET mykey
VALUE mykey 0 5
hello
END
# Delete a key
DELETE mykey
DELETED

# Verify deletion
GET mykey
END

Architecture

MirDB uses an LSM-tree (Log-Structured Merge-tree) architecture for efficient write performance and persistent storage.

Write Path

When data is written, it first goes to the Write-Ahead Log (WAL) for durability. Then the data is inserted into the in-memory Memtable (implemented as a skip list). When the memtable reaches its size threshold, it is flushed to disk as an immutable SSTable at Level 0. Background compaction merges and sorts SSTables across levels.

Read Path

Reads first check the Memtable for the most recent data. If not found, the search continues through SSTables starting from Level 0 (newest data) and proceeding to higher levels. Bloom filters and block indexes optimize lookups for efficient read performance.
