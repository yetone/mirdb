MirDB

Persistent Key-Value Storage, Memcached Simplicity

A persistent key-value store with Memcached protocol compatibility

Get Started View on GitHub

Key Features

Memcached Protocol Support

Fully compatible with existing memcached clients. Drop-in replacement that works with your current infrastructure and client libraries.

Persistence

Data survives restarts unlike traditional memcached. Your cached data persists to disk, ensuring durability and eliminating cache warm-up delays.

LSM Tree Architecture

Efficient storage with memtables and SSTable compaction. Write-optimized architecture that provides excellent performance for write-heavy workloads.

High Performance

Built for speed with skip list data structures and efficient memory management. Handles high-throughput workloads with minimal latency.

Rust Implementation

Memory safety and performance benefits from Rust. Zero-cost abstractions and compile-time guarantees for reliable, secure operation.

Skip List

Fast in-memory operations using skip list data structure. O(log n) search, insert, and delete operations for efficient memtable management.

The diagram shows MirDB's LSM tree architecture with two main paths: Write Path: Client sends data to MirDB Server, which writes to Write-Ahead Log (WAL), then to Memtable (Skip List), when full becomes Immutable Memtable, then minor compaction to SSTable Level 0, and major compaction to deeper levels. Read Path: Client queries MirDB Server, which checks Memtable first, then Immutable Memtables if not found, finally checks SSTable levels from L0 to L2+ until value is found.

Write Path

MirDB uses a Log-Structured Merge (LSM) tree for efficient write operations:

  1. WAL (Write-Ahead Log): Every write operation is first recorded in the WAL for durability. This ensures data can be recovered after crashes.
  2. Memtable: Data is written to an in-memory skip list structure called the Memtable for fast write and lookup performance.
  3. Immutable Memtable: When the Memtable reaches its size limit, it becomes immutable and a new Memtable is created for incoming writes.
  4. SSTables: Immutable Memtables are flushed to disk as Sorted String Tables (SSTables), organized in levels for efficient storage.

Read Path

Reads follow a specific lookup order to find the most recent value:

  1. Memtable: First, MirDB checks the active Memtable for the requested key, as it contains the most recent writes.
  2. Immutable Memtables: If not found, the search continues through any Immutable Memtables awaiting flush to disk.
  3. SSTable Levels: Finally, MirDB searches through SSTable levels from L0 to deeper levels (L1, L2, etc.) until the key is found or confirmed absent.

Compaction Process

Compaction maintains storage efficiency and read performance:

Minor Compaction

When Immutable Memtables accumulate, they are flushed to SSTable Level 0. This process converts in-memory data to persistent disk storage while maintaining sorted order within each SSTable.

Major Compaction

When a level accumulates too many SSTables, major compaction merges them into the next level. This process removes deleted keys, merges duplicate entries, and maintains sorted order across levels for efficient range queries.

Quick Start

Get MirDB running in minutes

1. Build from Source

Clone the repository and build MirDB using Cargo:

# Clone the repository
git clone https://github.com/yetone/mirdb.git
cd mirdb

# Build the release version
cargo build --release

2. Configure MirDB

Create a configuration file (e.g., mirdb.toml) with your settings:

# Network configuration
addr = "0.0.0.0:12333"

# Storage settings
work_dir = "/var/lib/mirdb"
max_level = 7

# Memory table limits
mem_table_max_size = "4M"
mem_table_max_height = 32

# SSTable configuration
sst_max_size = "100M"
block_size = "4K"

# Compaction triggers
l0_compaction_trigger = 4

3. Start the Server

Launch the MirDB server with your configuration file:

# Start mirdb-server with config file
./target/release/mirdb-server -c mirdb.toml

# Or use the default configuration
./target/release/mirdb-server -c etc/mirdb.toml

4. Connect and Use

Use any Memcached client to connect. Here's an example using telnet:

# Connect to MirDB
telnet localhost 12333

# SET a value (key, flags, exptime, bytes)
set mykey 0 0 5
hello
STORED

# GET the value back
get mykey
VALUE mykey 0 5
hello
END

# DELETE the key
delete mykey
DELETED

Configuration Reference

Configure MirDB to match your workload and environment

Example Configuration File

# MirDB Configuration (default.conf)
addr = "0.0.0.0:12333"
work_dir = "/tmp/mirdb"
mem_table_max_size = "4M"
sst_max_size = "100M"
max_level = 7
l0_compaction_trigger = 4
mem_table_max_height = 32
imm_mem_table_max_count = 16
block_size = "4K"
block_restart_interval = 16
thread_sleep_ms = 500

Configuration Options

Option Default Description
addr 0.0.0.0:12333 Listen address and port for the MirDB server. Accepts connections from all interfaces on port 12333 by default.
work_dir /tmp/mirdb Working directory for storing data files including WAL, SSTables, and metadata. Use a persistent location in production.
mem_table_max_size 4M Maximum size of the active memtable before it becomes immutable. Larger values reduce write amplification but increase memory usage.
sst_max_size 100M Maximum size of each SSTable file. Controls the granularity of compaction and affects read performance.
max_level 7 Maximum number of levels in the LSM tree. More levels allow for larger datasets but may increase read latency.
l0_compaction_trigger 4 Number of Level 0 SSTables that triggers compaction. Lower values reduce read amplification at the cost of more frequent compactions.
mem_table_max_height 32 Maximum height of the skip list in the memtable. Higher values improve lookup performance for large memtables.
imm_mem_table_max_count 16 Maximum number of immutable memtables before writes are stalled. Increase if flush rate cannot keep up with write rate.
block_size 4K Size of data blocks in SSTables. Larger blocks improve compression but may increase read amplification.
block_restart_interval 16 Number of keys between restart points in SSTable blocks. Affects the trade-off between space efficiency and random access speed.
thread_sleep_ms 500 Sleep interval in milliseconds for background threads when idle. Lower values increase responsiveness but use more CPU.

When to Choose MirDB

MirDB is the ideal choice when you need:

  • Persistence with Memcached compatibility - If you're using memcached but need your data to survive restarts, MirDB is a drop-in replacement that adds durability without changing your client code.
  • Simple key-value storage with durability - When you don't need Redis's complex data structures but require reliable persistence, MirDB offers a streamlined solution.
  • Write-optimized workloads - The LSM tree architecture excels at handling high write throughput while maintaining good read performance.
  • Memory safety guarantees - Built in Rust, MirDB provides compile-time memory safety guarantees without sacrificing performance.
