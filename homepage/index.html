MirDB

A Persistent Key-Value Store with Memcached Protocol

Drop-in replacement for Memcached with persistence. Built on LSM Tree architecture for high-performance storage that survives restarts.

Quick Start
Scroll

Key Features

MirDB combines the simplicity of Memcached with the durability of persistent storage.

Memcached Protocol

Full compatibility with the standard memcached text protocol. Use your existing memcached clients and tools seamlessly - no code changes required. Supports SET, GET, DELETE, and more.

Persistence

Unlike traditional memcached, MirDB persists your data to disk using SSTables (Sorted String Tables). Your data survives restarts and crashes with write-ahead logging for durability.

LSM Tree Architecture

Built on a Log-Structured Merge-tree design with in-memory memtables and tiered SSTable levels. Optimized for write-heavy workloads while maintaining efficient reads through level organization.

Compaction

Automatic background compaction maintains optimal performance. Minor compaction flushes memtables to Level 0, while major compaction merges SSTables across levels to reclaim space.

See it in Action

Quick Start

Get MirDB up and running in minutes with these simple steps.

1

Install MirDB

Clone the repository and build from source using Cargo, Rust's package manager.

bash 
# Clone the repository
git clone https://github.com/example/mirdb.git
cd mirdb

# Build with Cargo
cargo build --release
2

Start the Server

Launch MirDB with a configuration file. The server listens on port 12333 by default.

bash 
# Start MirDB with config file
mirdb -c config.toml

# Or use the default configuration
./target/release/mirdb-server -c etc/mirdb.toml
3

Connect and Use

Use any Memcached client or telnet to connect. MirDB supports standard SET and GET commands.

bash 
# Connect using telnet
telnet localhost 12333

# Store a value (SET key flags ttl bytes)
set mykey 0 0 5
hello
# Response: STORED

# Retrieve the value
get mykey
# Response: VALUE mykey 0 5
#           hello
#           END

Sample Configuration

Create a config.toml file to customize MirDB settings:

toml 
# MirDB Configuration
addr = "0.0.0.0:12333"
work_dir = "/var/lib/mirdb"
max_level = 7

# Memory settings
mem_table_max_size = "4M"
sst_max_size = "100M"

Architecture

MirDB is built on a Log-Structured Merge-tree (LSM Tree) storage engine, optimized for write-heavy workloads while maintaining efficient reads.

Memtable

The memtable is an in-memory write buffer implemented as a skip list data structure. All incoming writes are first recorded here, providing O(log n) insert and lookup performance. When the memtable reaches its configured size threshold (default 4MB), it becomes immutable and is queued for flushing to disk.

  • In-memory skip list for fast writes
  • Configurable size threshold
  • Supports concurrent read access

SSTable

SSTable (Sorted String Table) is the persistent on-disk storage format used by MirDB. Data is organized into sorted, immutable files with block-based structure for efficient random access. Each SSTable includes a cuckoo filter for fast negative lookups and supports Snappy compression.

  • Sorted String Table for disk persistence
  • Block-based format with index
  • Cuckoo filter for bloom-like lookups
  • Snappy compression support

Write-Ahead Log (WAL)

The Write-Ahead Log (WAL) ensures durability by persisting every write to disk before acknowledging it. In the event of a crash, the WAL enables complete crash recovery by replaying uncommitted operations. WAL segments correspond to memtables and are cleaned up after successful compaction.

  • Write-ahead logging for durability
  • Crash recovery via log replay
  • Snappy-compressed records
  • Automatic segment cleanup

Compaction

MirDB uses a two-phase compaction strategy to maintain optimal performance. Minor compaction flushes immutable memtables to Level 0 SSTables. Major compaction (level compaction) merges SSTables across levels, eliminating duplicates and maintaining sorted order within each level.

  • Minor compaction: memtable to Level 0 SSTable
  • Major compaction: level-based merging
  • Background threads for non-blocking operation
  • Configurable triggers and thresholds

Read Path

When reading a key, MirDB searches in order of recency: first the active memtable, then immutable memtables (newest first), and finally SSTable levels starting from Level 0. Level 0 uses linear search (files may overlap), while Level 1+ uses binary search within sorted, non-overlapping files.

API Reference

MirDB implements the Memcached text protocol. Use any standard Memcached client to interact with MirDB.

Storage Commands

Commands for storing data in the database.

SET

Storage

Store a key-value pair. Overwrites any existing value for the key.

Syntax
set <key> <flags> <ttl> <bytes> [noreply]
Example
memcached 
set mykey 0 3600 5
hello
STORED

ADD

Storage

Store a key-value pair only if the key does not already exist.

Syntax
add <key> <flags> <ttl> <bytes> [noreply]
Example
memcached 
add newkey 0 0 5
world
STORED

REPLACE

Storage

Store a key-value pair only if the key already exists.

Syntax
replace <key> <flags> <ttl> <bytes> [noreply]
Example
memcached 
replace mykey 0 3600 6
world!
STORED

APPEND

Storage

Append data to an existing value.

Syntax
append <key> <flags> <ttl> <bytes> [noreply]
Example
memcached 
append mykey 0 0 6
_added
STORED

PREPEND

Storage

Prepend data to an existing value.

Syntax
prepend <key> <flags> <ttl> <bytes> [noreply]
Example
memcached 
prepend mykey 0 0 7
prefix_
STORED

Retrieval Commands

Commands for retrieving data from the database.

GET

Retrieval

Retrieve one or more keys from the database.

Syntax
get <key1> [<key2> ...]
Example
memcached 
get mykey
VALUE mykey 0 5
hello
END

GETS

Retrieval

Retrieve keys with CAS (Check-And-Set) token. In MirDB, this behaves identically to GET.

Syntax
gets <key1> [<key2> ...]
Example
memcached 
gets mykey otherkey
VALUE mykey 0 5
hello
VALUE otherkey 0 5
world
END

Deletion Commands

Commands for removing data from the database.

DELETE

Deletion

Remove a key from the database.

Syntax
delete <key> [noreply]
Example
memcached 
delete mykey
DELETED

MirDB-Specific Commands

Extended commands unique to MirDB for database management.

INFO

MirDB

Display database status and level information. This command is specific to MirDB and provides insights into the LSM tree structure.

Syntax
info
Example
memcached 
info
MirDB Status:
Level 0: 2 SSTables
Level 1: 5 SSTables
Memtable size: 2.1MB
END

MAJOR_COMPACTION

MirDB

Trigger a manual major compaction. This merges SSTables across levels to reclaim space and improve read performance.

Syntax
major_compaction
Example
memcached 
major_compaction
OK

Response Codes

Standard response codes returned by MirDB commands.

STORED

Data stored successfully

NOT_STORED

Data not stored (condition not met for add/replace)

EXISTS

CAS check failed (item has been modified)

NOT_FOUND

Key not found (for delete/replace operations)

DELETED

Key deleted successfully

ERROR

Unknown command or syntax error

Configuration

Customize MirDB behavior with these tunable parameters. Configuration uses TOML format.

Network

Parameter Description Default
addr Listen address and port for memcached connections 0.0.0.0:12333

Storage

Parameter Description Default
work_dir Directory path for data files (SSTables, WAL) /tmp/mirdb
max_level Maximum number of LSM tree levels 7

Memory Tables

Parameter Description Default
mem_table_max_size Maximum memtable size before flush to disk 4M (4MB)
mem_table_max_height Skip list maximum height 32
imm_mem_table_max_count Maximum queued immutable memtables 16

SSTables

Parameter Description Default
sst_max_size Maximum SSTable file size 100M (100MB)
block_size Data block size within SSTables 4K (4KB)
block_restart_interval Key prefix restart interval 16

Compaction

Parameter Description Default
l0_compaction_trigger Number of Level 0 files before compaction triggers 4
thread_sleep_ms Background thread sleep interval 500 (ms)

Size Units

Configuration parameters that specify sizes support the following suffixes:

  • K - Kilobytes (1,024 bytes)
  • M - Megabytes (1,024 KB)
  • G - Gigabytes (1,024 MB)
  • T - Terabytes (1,024 GB)

Example Configuration

Create a config.toml file with your desired settings:

toml 
# MirDB Configuration File

# Network Settings
addr = "0.0.0.0:12333"

# Storage Settings
work_dir = "/var/lib/mirdb"
max_level = 7

# Memory Table Settings
mem_table_max_size = "4M"
mem_table_max_height = 32
imm_mem_table_max_count = 16

# SSTable Settings
sst_max_size = "100M"
block_size = "4K"
block_restart_interval = 16

# Compaction Settings
l0_compaction_trigger = 4
thread_sleep_ms = 500

./target/release/mirdb-server -c etc/mirdb.toml

Performance

MirDB is designed for high-throughput write workloads while maintaining efficient reads through its LSM Tree architecture.

High Write Throughput

Sequential Writes

LSM Tree architecture optimizes for write-heavy workloads. All writes go to the in-memory memtable first, then batch-flush to disk via compaction.

Low Read Latency

In-Memory + Bloom Filter

Hot data served from memtable. Cuckoo filters provide fast negative lookups, minimizing unnecessary disk reads for missing keys.

Durability

Write-Ahead Log

Every write is recorded to the Write-Ahead Log before acknowledgment, ensuring data survives crashes and power failures.

Space Efficient

Compaction + Compression

Background compaction reclaims deleted keys and merges files. Snappy compression reduces storage footprint without sacrificing speed.

Performance Characteristics

Write Pattern Optimized for sequential writes
Read Pattern Fast point lookups via bloom filters
Memory Usage Configurable memtable size (default 4MB)
Compression Snappy compression for SSTables and WAL

Note: Actual performance varies based on hardware, configuration, and workload characteristics. Use the INFO command to monitor real-time database metrics and SSTable levels.

Contributing

We welcome contributions from the community. Here's how you can get involved and help improve MirDB.

Development Setup

Get your development environment ready to contribute to MirDB.

  1. Install Rust: MirDB requires Rust toolchain. Install via rustup
  2. Clone the repository: git clone https://github.com/example/mirdb.git
  3. Build the project: cargo build
  4. Run tests: cargo test to ensure everything works

How to Contribute

Follow these steps to submit your contributions via Pull Requests.

  1. Fork the repository to your GitHub account
  2. Create a feature branch: git checkout -b feature/your-feature
  3. Make your changes and commit with clear messages
  4. Submit a Pull Request with a description of your changes

Reporting Issues

Found a bug or have a feature request? Let us know!

  • Check existing issues to avoid duplicates
  • Provide clear steps to reproduce bugs
  • Include MirDB version and environment details
  • Use descriptive titles for feature requests

Code Style Guidelines

Maintain code quality by following these guidelines.

  • Ensure cargo clippy passes without warnings
  • Write tests for new features and bug fixes
  • Keep commits focused and atomic
