MirDB

A persistent key-value store with memcached protocol compatibility. Drop-in replacement for memcached that persists your data.

Get Started View on GitHub

See It In Action

Features

Persistent Storage

Unlike memcached, MirDB persists data to disk using SSTables, ensuring your data survives restarts.

Memcached Protocol

Compatible with standard memcached text protocol. Use your existing memcached clients seamlessly.

LSM Tree Architecture

Log-Structured Merge-tree approach with memtables and multi-level SSTable compaction for optimal performance.

Skip-List Memtable

Efficient in-memory data structure providing O(log n) operations for fast reads and writes.

Automatic Compaction

Background minor and major compaction keeps the database optimized without manual intervention.

Async I/O with Tokio

Built on Tokio for high-performance async networking, handling thousands of concurrent connections.

Quick Start

Get MirDB running in minutes. Follow these simple steps to start storing your data persistently.

1 Build and Start the Server 

# Clone the repository
git clone https://github.com/yetone/mirdb.git
cd mirdb

# Build and run with Cargo
cargo run --release

# Server starts on port 12333

2 Store Data with SET 

# Connect using telnet or any memcached client
telnet localhost 12333

# SET command format: set <key> <flags> <ttl> <bytes>
set mykey 0 0 5
hello
STORED

3 Retrieve Data with GET 

# GET command retrieves stored values
get mykey
VALUE mykey 0 5
hello
END

Other Commands

MirDB supports standard memcached commands:

  • add - Add if key doesn't exist
  • replace - Replace existing key
  • delete - Delete a key
  • append - Append to value
  • prepend - Prepend to value
  • info - Database status

Architecture

MirDB uses a Log-Structured Merge-tree (LSM tree) architecture, combining fast in-memory writes with efficient disk-based persistence.

                        │                   WRITE REQUEST                       │
                        └─────────────────────────┬───────────────────────────────┘
                                                  │
                                                  ▼
                        ┌─────────────────────────────────────────────────────┐
                        │                  WRITE-AHEAD LOG (WAL)              │
                        │   Durability guarantee - survives crashes            │
                        └─────────────────────────┬───────────────────────────────┘
                                                  │
                                                  ▼
                        ┌─────────────────────────────────────────────────────┐
                        │                     MEMTABLE                        │
                        │   In-memory skip list - fast O(log n) operations    │
                        └─────────────────────────┬───────────────────────────────┘
                                                  │ (when full)
                                                  ▼
                        ┌─────────────────────────────────────────────────────┐
                        │               IMMUTABLE MEMTABLES                   │
                        │   Queue of memtables awaiting flush to disk          │
                        └─────────────────────────┬───────────────────────────────┘
                                                  │ (minor compaction)
                                                  ▼
┌─────────────────────────────────────────────────────────────────────────────────────────────┐
│                                    SSTABLE LEVELS (DISK)                                    │
├─────────────────────────────────────────────────────────────────────────────────────────────┤
│  Level 0   │  Recently flushed SSTables - may have overlapping key ranges                   │
├────────────┼────────────────────────────────────────────────────────────────────────────────┤
│  Level 1+  │  Sorted, non-overlapping SSTables - optimized for reads                        │
└────────────┴────────────────────────────────────────────────────────────────────────────────┘
                                                  ▲
                                                  │ (major compaction)
                              Merges and reorganizes SSTables between levels

LSM Tree

The Log-Structured Merge-tree is a data structure optimized for high write throughput. It buffers writes in memory and periodically flushes them to disk in sorted batches, avoiding random I/O. MirDB uses this approach to combine memcached-like speed with persistent storage, making it ideal for write-heavy workloads.

Memtable

The memtable is an in-memory write buffer implemented as a skip list. All incoming writes are first stored here, providing O(log n) insert and lookup operations. When the memtable reaches capacity (default 4MB), it becomes immutable and a new memtable takes over. This design allows for fast writes without blocking.

SSTable

Sorted String Tables (SSTables) are immutable, sorted files that store key-value pairs on disk. Data is organized into blocks with prefix compression and includes a cuckoo filter for efficient negative lookups. SSTables are organized in levels, with Level 0 containing recently flushed data and higher levels containing merged, non-overlapping data.

Write-Ahead Log (WAL)

The Write-Ahead Log ensures data durability by persisting every write to disk before acknowledging it. If MirDB crashes, the WAL is replayed during recovery to restore any data not yet flushed to SSTables. WAL entries are Snappy-compressed and aligned for efficient I/O.

Data Paths

Write Path

  1. Write to WAL for durability
  2. Insert into active memtable
  3. Acknowledge to client
  4. Background: flush to SSTable when full

Read Path

  1. Check active memtable
  2. Check immutable memtables
  3. Search Level 0 SSTables
  4. Binary search higher levels

MirDB vs Memcached

MirDB provides the same protocol compatibility as memcached while adding critical persistence features.

Feature MirDB Memcached
Data Persistence Yes No
Memcached Protocol Yes Yes
LSM Tree Storage Yes No
Drop-in Replacement Yes —
Data Survives Restart Yes No
Async I/O (Tokio) Yes libevent

Key Differentiator: Persistence

While memcached is an in-memory cache that loses data on restart, MirDB persists your data to disk using SSTables and Write-Ahead Logging (WAL). This means your data survives server restarts, making MirDB ideal for use cases where cache durability matters.

MirDB uses the same text protocol as memcached, allowing you to use existing memcached clients without modification.

Supported Commands

MirDB implements the memcached text protocol. Use your existing memcached clients with these commands.

GET

Retrieve Values

Retrieves the value associated with the key. Supports multiple keys in a single request.

get <key> [<key2> ...]
GETS

Get with CAS Token

Like GET but also returns a CAS token for check-and-set operations.

gets <key> [<key2> ...]
SET

Store Data

Stores data, overwriting any existing value for the key.

set <key> <flags> <ttl> <bytes>
<data>
ADD

Add if Not Exists

Stores data only if the key does not already exist.

add <key> <flags> <ttl> <bytes>
<data>
REPLACE

Replace Existing

Stores data only if the key already exists.

replace <key> <flags> <ttl> <bytes>
<data>
DELETE

Delete Key

Removes the key and its associated value from the store.

delete <key> [noreply]
APPEND

Append to Value

Appends data to the end of an existing value.

append <key> <flags> <ttl> <bytes>
<data>
PREPEND

Prepend to Value

Prepends data to the beginning of an existing value.

prepend <key> <flags> <ttl> <bytes>
<data>
INFO

Database Status

Returns information about the database status and statistics.

info
